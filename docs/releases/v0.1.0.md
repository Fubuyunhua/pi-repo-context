# pi-repo-context v0.1.0

Release date: 2026-08-28

This is the stable release record for the approved `v0.1.0` payload. The presence of the reviewed immutable
`v0.1.0` tag in the repository is the source of truth for release availability. This document records the release; it
does not create or publish a commit, tag, package, or GitHub release.

## Approved payload and compatibility

- Tool-first surface: `repo_context_search`, `repo_context_status`, and `/repo-context status|rebuild|doctor` are the
  primary interfaces. `context_vault_repo_map` is a deprecated `0.1.x` search alias planned for removal in `0.2.0`.
- There is no automatic context injection, cross-plugin API, or runtime dependency. Planner/Renderer/Projection Cache
  work, Provider experiments, gold tasks, research reports, and legacy bench assets are not included.
- Exact tested peers are `@earendil-works/pi-coding-agent` `0.84.1` and `typebox` `1.3.7`. The package version is
  `0.1.0` and requires Node.js `>=22.19.0`.
- The approved tag must resolve to the final release commit containing this record and the validated package manifest.

## Snapshot, Graph, Resolver, and freshness

Persisted Repo Map generations retain structural `schemaVersion: 1` and provenance
`pi-repo-context` / `0.1.0`, with TypeScript and optional `java-parser@3.0.1` analyzer provenance. Immutable Snapshot
handles use `repository-snapshot/v1`, content identity, workspace revision, Git HEAD, generation, dirty files, pending
paths, diagnostics, and explicit `fresh|dirty|stale|unsupported` freshness.

Repository Graph v1 (`repository-graph/v1`) and Resolver v1 are deterministic, bounded, derived in memory from one
validated Snapshot. Domain-separated node/reference/evidence/edge identities and resolution evidence preserve source
provenance; unresolved and ambiguous relations remain explicit rather than guessed. Graph state is not persisted.

A chokidar watcher marks relevant changes pending. Search and capture reconcile watcher input, dirty workspace state,
and current Git HEAD before reporting results; failures or bounded pending work are labeled rather than silently
reported fresh.

## State, migration, and rollback

The first Repo Context startup cold-builds from repository source under:

```text
${PI_CODING_AGENT_DIR}/pi-repo-context/projects/<projectId>/repo-map
```

It does not read, move, adopt, prune, or delete legacy Context Vault Repo Map state or Observation data. Canonical owned
state components are identity-checked and isolated from the legacy root. Node has no portable `openat` API, so a
same-account or privileged process racing a canonical owned-ancestor rename between validation and a path-based
operation remains a narrow residual TOCTOU risk.

Before using Repo Context beside a pre-split monolith, set `repoMapEnabled:false` and `mapInjectionMode:"off"`, stop the
old session, and restart Pi. For rollback, stop and disable Repo Context, restart, retain both state roots, and return to
the reviewed pre-split checkpoint if repository behavior must be restored. No state conversion or deletion is needed.
See [`../MIGRATION.md`](../MIGRATION.md).

## Installation

Verify that the reviewed immutable tag exists in the repository before using the exact release install command:

```bash
git ls-remote --exit-code --tags https://github.com/Fubuyunhua/pi-repo-context.git refs/tags/v0.1.0
pi install git:github.com/Fubuyunhua/pi-repo-context@v0.1.0
```

For local development without relying on a tag:

```bash
git clone https://github.com/Fubuyunhua/pi-repo-context.git
cd pi-repo-context
npm ci
pi -e ./extensions/index.ts
```

To roll back a tagged install, stop Repo Context, restart Pi, select the previously reviewed immutable version or the
disabled state, and do not delete either state root.

1. Review the exact payload and validation results.
2. Confirm the immutable `v0.1.0` tag resolves to the approved payload commit.
3. Push the commit and tag only with separate authorization.
4. Verify the remote tag is present, then run the exact tagged install command and acceptance smoke.
5. Publish any package or GitHub release only with separate authorization, and record that publication independently.
